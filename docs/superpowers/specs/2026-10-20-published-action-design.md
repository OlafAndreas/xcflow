# Published install action, pinned by commit, bumped by Dependabot

Design for moving the GitHub Actions install step out of every repo that `xcflow setup` configures and into one published action, `OlafAndreas/xcflow-action`.

## Why

Today `xcflow setup` writes `.github/actions/xcflow/action.yml` into each repo: a composite action that downloads the pinned xcflow release, verifies its checksum and puts it on the PATH. The three generated workflows use it. Every xcflow release therefore means a manual `xcflow setup` run and a PR in every repo, or the repo stays behind. The Sylvia repo sits on 0.2.6 while 0.2.7 is out, one day after setting it up.

Publishing the action once and referencing it by commit from the generated workflows keeps the pin in the repo and makes Dependabot do the bumping. The repo still shows exactly which xcflow version its CI runs, and a reviewer still approves every change.

## Goals

- The three generated workflows install xcflow with `uses: OlafAndreas/xcflow-action@<commit sha> # vX.Y.Z`. No local action file is written any more.
- Every xcflow release also publishes the matching version of the action, tagged `vX.Y.Z` in `OlafAndreas/xcflow-action`, from one template kept in the xcflow repo.
- `setup` adds a Dependabot config so the pin moves by pull request when a new version is out, and the `Plan Xcode Cloud workflow changes` check runs on those pull requests.
- A repo set up with an earlier xcflow migrates on its next `xcflow setup`: an untouched local action is removed, an edited one is kept and named in the to-do list.
- Integrity stays what it is: commit → `action.yml` → checksum → tarball, all reviewable.

## Non-goals

- A moving major tag (`@v0`) and a GitHub Marketplace listing. Tags `vX.Y.Z` are all Dependabot and `uses:` need. Either can be added later without changing any repo.
- A macOS build in the action. The generated workflows run on `ubuntu-latest`, and the action stays Linux-only as decided in PR #2. Adding macOS later is a change to the action only.
- GitHub releases in the action repo. Tags are enough.

## Anti-goals

- A repo's CI picking up a new xcflow version without a reviewed change in that repo. That is why the pin is a commit, not a tag.
- Deleting a file the user has edited.
- Documenting two install paths. The local action disappears from `setup`'s output and from the README.

## Constraints that shape the design

- `uses:` takes no expressions, so the commit is literal text in each workflow, and the release's verify job can't `uses:` a commit it only learns at run time. It checks out the action repo at the tag and uses that path.
- Dependabot updates a commit-pinned action and keeps the `# vX.Y.Z` comment current, as long as the comment is there and the action repo has version tags.
- Workflows that Dependabot's pull requests trigger run with a read-only token and **without the repo's Actions secrets**. They see Dependabot secrets instead. The plan check talks to App Store Connect, so it needs the three `ASC_*` secrets there too. See "Secrets for Dependabot's pull requests".
- xcflow has no YAML parser. `.github/dependabot.yml` is handled at text level: create it, recognise an existing `github-actions` entry, otherwise leave the file alone and say what to add.
- `setup` needs the commit of its own version's tag in the action repo. `git ls-remote` gives it without authentication or API rate limits.

## The action repo: `OlafAndreas/xcflow-action`

Public. Contains:

- `action.yml`: the composite action, as generated today, with the version, archive names and checksums filled in for that release. Linux x86_64 and arm64, checksum verified, `--version` printed.
- `README.md`: a short note that `xcflow setup` pins this action by commit in the workflows it writes, that Dependabot bumps it, that each xcflow release publishes a matching tag here, and that the file is generated by xcflow's release workflow and not edited by hand.
- `LICENSE`: MIT, copied from xcflow.

One commit per xcflow release, message `xcflow X.Y.Z`, lightweight tag `vX.Y.Z` on that commit. Lightweight so the tag's own sha is the commit sha.

No CI of its own. xcflow's release workflow verifies the action, see below.

### Prerequisites the owner does once

- Create the empty public repo `OlafAndreas/xcflow-action`.
- A token with contents write access on it, stored in the xcflow repo as the `ACTION_TOKEN` secret. If `TAP_TOKEN`'s scope is widened to include the new repo, the workflow can use that instead; the name in the workflow is the builder's call, `ACTION_TOKEN` is the suggestion.

## Where the action's source lives

The action template moves out of `Templates.swift` into a file in the xcflow repo, `Action/action.yml`, with the placeholders it has today: `{{version}}`, `{{archive-linux-x86_64}}`, `{{checksum-linux-x86_64}}`, `{{archive-linux-aarch64}}`, `{{checksum-linux-aarch64}}`. A YAML file is readable and diffable, and the binary no longer carries release machinery.

The Swift side keeps a frozen copy of the last version of the local action template, used only to recognise an untouched local action during migration. It is never written.

## Release workflow changes

In the `publish` job of `.github/workflows/release.yml`, after the GitHub release is created and **before** the Homebrew formula is updated, so nobody can `brew upgrade` and run `setup` before the action tag exists:

1. Render `Action/action.yml` with the version and the checksums from `dist/checksums.txt`.
2. Clone `OlafAndreas/xcflow-action` with the token, write `action.yml`, `README.md` and `LICENSE`, commit as `github-actions[bot]` with message `xcflow X.Y.Z`, tag `vX.Y.Z`, push the branch and the tag.

The `verify` job changes from using the local action to:

- Check out `OlafAndreas/xcflow-action` at `refs/tags/${{ github.ref_name }}` into `action/`, and on Linux runners `uses: ./action` to install xcflow. Check `xcflow --version` matches the release.
- Run the released binary's `setup` into `smoke/` as today, then check that the three workflows in `smoke/` contain `OlafAndreas/xcflow-action@<sha> # vX.Y.Z` where `<sha>` is `git rev-parse HEAD` of `action/`, that `smoke/.github/dependabot.yml` exists, and that no `.github/actions/` folder was written.
- Keep the existing plan smoke test against the fixtures.

The job order makes the release fail loudly if the action push failed, before anyone installs the version.

## `setup` changes

### What it writes

- `.github/workflows/xcflow-plan.yml`, `xcflow-apply.yml`, `xcflow-sync.yml`: the `Install xcflow` step becomes `uses: OlafAndreas/xcflow-action@<sha> # vX.Y.Z`. The `paths:` filters drop `.github/actions/xcflow/**`.
- `.github/dependabot.yml`:

  ```yaml
  version: 2
  updates:
    - package-ecosystem: github-actions
      directory: /
      schedule:
        interval: weekly
  ```

  Status rules: missing → created. Present and containing a `github-actions` package ecosystem entry, quoted or not → unchanged. Present without one → kept, reported like other differing files, with a to-do that quotes the entry to add. Weekly is the interval because a bump needs a review anyway and more often than that is noise; this is the designer's call, not a requirement.
- `XcodeCloud/README.md`, the skill and the rule: wording that mentions `.github/actions/xcflow/` changes to name the published action.
- `.github/actions/xcflow/action.yml` is no longer written. The `--checksums` option, the checksum download and the "Add the release checksums" to-do go away with it.

### Resolving the commit

`setup` runs `git ls-remote --tags https://github.com/OlafAndreas/xcflow-action.git vX.Y.Z` for its own `Version.current`. It takes the peeled `^{}` line if there is one, otherwise the plain line, so an annotated tag would still resolve to a commit. The dry run resolves too, since it only reads, in line with the dry run fetching checksums today.

A new option `--action-sha <sha>` skips the lookup. Tests use it; so can an offline run.

If the lookup fails or finds no tag, which happens offline and for a development build whose version isn't released yet, `setup` writes `uses: OlafAndreas/xcflow-action@vX.Y.Z` and adds a to-do: pin the action to its commit in the three workflows once the tag exists. The repo still works, and Dependabot still proposes updates to a tag reference.

### Migration of an existing repo

After writing the files, if `.github/actions/xcflow/action.yml` exists:

- Parse the version from the `Install xcflow X.Y.Z` step name and the two `SUM="…"` values. Render the frozen legacy template with them. If the file equals the result byte for byte, it is untouched: remove it, then remove `.github/actions/xcflow/` and `.github/actions/` if they are now empty. Report `Removed .github/actions/xcflow/action.yml, replaced by OlafAndreas/xcflow-action`. The dry run reports `Would remove …`.
- Otherwise keep it, report it as differing, and add a to-do: remove `.github/actions/xcflow/`, the workflows now install xcflow from `OlafAndreas/xcflow-action`. `--force` removes it regardless, in line with what `--force` means for the other files.

Files generated by versions older than the frozen template won't match and get the to-do. That is accepted.

### Secrets for Dependabot's pull requests

The plan check on a Dependabot pull request is exactly the test that the new xcflow version still works against App Store Connect, so it must run. Dependabot-triggered workflows can't read Actions secrets, only Dependabot secrets, and their `GITHUB_TOKEN` is read-only unless the workflow asks for more.

- When `setup` sets the three secrets, with the flags or from the prompts, it sets each one twice: `gh secret set NAME` and `gh secret set NAME --app dependabot`. Same value, same repo, same admins.
- The "already set" check looks at both stores. All three present in both → skip. Present in Actions but not Dependabot → treated like missing secrets: offer to set, or set from the flags, and a to-do if declined. The message says which store is short.
- `--replace-secrets` replaces both.
- The plan workflow already declares `permissions: pull-requests: write` for its comment; the builder checks it is at the workflow level so it also applies to Dependabot-triggered runs.

If the owner would rather not duplicate the key, the alternative is to skip the plan job when `github.actor == 'dependabot[bot]'`, at the cost of merging bumps untested. This design takes the duplication; it is the one choice here the owner should confirm.

## Rollout

1. Owner: create the action repo and the token secret.
2. xcflow pull request with everything above, tests included. Merge.
3. Release 0.2.8. The release publishes `xcflow-action` v0.2.8 and the verify job proves `setup` pins to it.
4. Sylvia: `xcflow setup --yes`. It removes the untouched local action, rewrites the three workflows, adds `dependabot.yml`, and sets the three Dependabot secrets from the key. Pull request, plan check runs through the published action, merge.

Until step 3 is done, a `setup` from a development build falls back to the tag reference with a to-do, which is fine for testing and wrong for nothing.

## Tests

- Generated workflows contain the given `--action-sha` with the version comment, and no `.github/actions/` path is written.
- Without a resolvable commit, the workflows reference the tag and the to-do names the pin.
- `dependabot.yml`: created, unchanged when an entry exists in either quoting, kept with a to-do when the file lacks one.
- Migration: untouched legacy action removed with its empty folders; edited one kept with a to-do; `--force` removes it; dry run writes and removes nothing.
- Secrets: set to both stores; present in Actions only counts as missing; `--replace-secrets` replaces both. Through the existing `SecretStore` seam, which grows an `app` parameter.
- Release workflow: covered by the verify job, not by unit tests.

## Left to the builder

- Exact wording of messages and to-dos, following the existing voice.
- Whether `ls-remote` runs through the existing `run(_:in:)` helper or a dedicated one; how failures map to the fallback.
- The shape of the `SecretStore` change for the two stores.
- How the release step renders the placeholders: `sed`, or a few lines of shell. Not Swift.
- Where the frozen legacy template lives in the Swift sources.
